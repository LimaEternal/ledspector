# LEDSpector — Linux (headless)

Скрипты подготовлены под Linux-сервер без GUI. Графическая разметка не используется, всё выводится в консоль. Сетку для первоначальной разметки формируем **тем же кодом на сервере** (тот же OpenCV/V4L2, то же разрешение 1280x720), чтобы координаты однозначно совпадали с live-захватом.

## 1. Разделение ответственности

- **run_linux.py (grid)** — снимает кадр с камеры на сервере, сохраняет `snapshot_raw.png` и `snapshot_grid.png` в PNG. По `snapshot_grid.png` ты читаешь координаты X,Y прямо с картинки и заполняешь `config/leds.tsv`.
- **run_linux.py (exposure)** — интерактивный подбор ручной экспозиции `exposure_time_absolute` с выводом средней яркости по каждому ROI.
- **run_linux.py (monitor/log)** — headless-наблюдение в реальном времени: таблица с перерисовкой + лог изменений состояний.

Windows-код (`run.py`, `scrcpy*`, `src/led_emulator.py`, GUI-тесты) **не трогали** — оставлен как есть.

## 1a. Формат камеры: почему MJPG, а не YUYV

Это главная тонкость настройки, на которой легко потерять разрешение.

`v4l2-ctl --list-formats-ext` на сервере показывает:

```
MJPG: 480x320@25, 640x480@25, 1280x720@20
YUYV: 320x240@25, 640x480@10
```

**1280x720 существует только в MJPG.** В несжатом YUYV максимум — 640x480, и всего 10 FPS.

Без явного указания формата OpenCV выбирает YUYV по умолчанию и получает 640x480@10 вместо запрошенных 1280x720. Разрешение «уплывает» молча, и координаты LED из конфига начинают указывать на другие пиксели — при этом кадры продолжают приходить, ошибки не видно.

Поэтому `CAP_PROP_FOURCC` выставляется **до** ширины и высоты (OpenCV применяет настройки строго по порядку). Задать формат после разрешения уже поздно.

Формат переключается флагом `--fourcc` (по умолчанию `mjpg`):

```bash
python3 run_linux.py monitor --fourcc mjpg    # 1280x720@20 — рабочий режим
python3 run_linux.py monitor --fourcc yuyv    # 640x480@10, без сжатия
```

### Про FPS

20 FPS для 720p — это **потолок камеры**, а не просадка: MJPG 1280x720 отдаёт только 20 кадров в секунду, и запрос 30 драйвер игнорирует. Для определения 1 и 4 Гц этого достаточно с запасом; 8 Гц уже не разобрать, потому что на частоте Найквиста 10 Гц.

В конфиге FPS не фиксируется (директивы `resolution` достаточно), поэтому расхождение «просили 30, получили 20» проверку не ломает.

### Про JPEG-артефакты и почему мы НЕ размываем кадр

MJPG — это сжатие JPEG на стороне камеры, и на ROI 2-5 px артефакты вполне возможны. Размытие тут **вредит**, а не помогает:

- ядро `GaussianBlur((5,5))` при `sigma=0` (OpenCV подставляет 1.1) сохраняет у центрального пикселя лишь **13,7%** собственного значения;
- **26,3%** веса ядра приходится на отражение краёв ROI — это значения, которых в кадре вообще нет;
- в итоге яркость диода смешивается с яркостью корпуса сервера, среднее по ROI падает, а вся классификация (`OFF` при V<40, `SOLID_ON` при V>60) едет по ложному сигналу.

Ядро 5x5 физически больше самой измеряемой области.

Что реально помогает:

1. **Временное усреднение** — уже встроено: `FrequencyAnalyser` копит историю по окну в 2 секунды, так что шум между кадрами сглаживается сам собой.
2. **Выравнивание ROI по сетке блоков 8x8** — JPEG кодирует блоками 8x8, и ROI, попавший на границу блока, даёт заметный скачок. Сдвиг координат так, чтобы ROI целиком лежал внутри блока, убирает разрыв без потери сигнала.
3. **Фильтр по запросу** (`medianBlur` предпочтительнее гаусса: он не смешивает фон, а выбирает реальное значение) — отложен: сначала нужно посмотреть на реальные артефакты, а не лечить их теоретически. Если шум по цвету окажется мешающим, добавим `--filter median`.

Если калибровка цвета потребует честных данных, есть запасной путь: `--fourcc yuyv` даёт несжатой картинку ценой разрешения и FPS.

## 2. Установка

```bash
cd /path/to/ledspector
pip install -r requirements-linux.txt
```

Важный момент: используем `opencv-python-headless`, а не `opencv-python`. Полный wheel OpenCV тянет GUI-библиотеки (libGL), на минимальном headless-сервере без них импорт `cv2` падает. `headless` лишён GUI-зависимостей и при этом содержит все нужные функции чтения/записи кадров.

## 3. Самопроверка

```bash
python3 run_linux.py check
```

Проверяет: Python, OpenCV/numpy, наличие `/dev/video*`, наличие `v4l2-ctl`, поддерживаемые форматы и разрешения (`--list-formats-ext`), возможность открыть камеру в MJPG 1280x720, разобранные режимы `auto_exposure` и список V4L2-контролов. Запускать **первым** после установки.

Признак того, что всё в порядке:

```
[camera] /dev/video0: запрошено MJPG 1280x720@30, получено MJPG 1280x720@20
/camera] /dev/video0 MJPG 1280x720@20 | exposure=500 mode=manual
режимы auto_exposure: {'manual': 1, 'auto': None, 'current': 1}
```

Если в выводе `получено YUYV 640x480` — fourcc не применился и координаты применять нельзя. Если `exposure=None` — не читается контрол экспозиции.

## 4. Доступ к камере (`/dev/video*`)

Камера скорее всего видна как `/dev/video0`. Если запуск от обычного пользователя, могут быть права.

Быстрый вариант (только на время сессии):

```bash
sudo usermod -aG video $USER
newgrp video  # или перелогиниться
```

Постоянное udev-правило:

```bash
sudo cat > /etc/udev/rules.d/99-uvc.rules << 'EOF'
KERNEL=="video*", MODE="0660", GROUP="video"
EOF
sudo udevadm control --reload-rules && sudo udevadm trigger
```

## 5. Снимок с сеткой для разметки (1280x720)

```bash
python3 run_linux.py grid
```

Создаст:

- `snapshot_raw.png` — сырой кадр без сетки (удобен для последующей калибровки цвета)
- `snapshot_grid.png` — кадр с **двойной сеткой**: тонкая каждые 10 px (полупрозрачная), жирная каждые 50 px + подписи X/Y по краям кадра. Подписи вынесены наружу, чтобы не закрывали панель.

По `snapshot_grid.png` в текстовом редакторе считываешь координаты центров светодиодов (X,Y). Заполняешь `config/leds.tsv`. Разрешение в шапке зафиксировано: `resolution: 1280 720` — при несовпадении разрешения кадра и конфига монитор выдаст ошибку.

Шаг сетки можно подправить при необходимости:

```bash
python3 run_linux.py grid --minor-step 5 --major-step 50
```

## 6. Конфиг `config/leds.tsv`

Формат с директивами в шапке:

```tsv
# LEDSpector — карта панели
#panel: VEGMAN-R220-front
resolution: 1280 720

# ID   X    Y    W    H   описание
PWR   482  231  5    5   питание
```

- `resolution` обязателен и должен совпадать с разрешением live-кадра (1280x720).
- `panel` — произвольное название, можно раскомментировать и использовать для нескольких панелей.
- Парсер терпим к пустым/битым строкам: он пропустит строку с предупреждением, не уронит процесс.
- Если ID повторяется — дубликат игнорируется с предупреждением.

Координаты — это верхний левый угол прямоугольника ROI `[x, y, w, h]`. Центр `cx = x+w//2, cy = y+h//2`. Для мелких диодов 2-5×2-5 достаточно.

## 7. Подбор экспозиции

Камера поддерживает ручной режим (`Auto Exposure = Manual Mode`). Сценарий перебора значений в консоли:

```bash
python3 run_linux.py exposure --config config/leds.tsv
```

- Enter без значения — повторить текущее.
- Число — установить `exposure_absolute` (автоматически приводится в диапазон камеры).
- `a` (auto) — вернуть автоэкспозицию.
- `q` — выход.

После каждой установки скрипт печатает фактическое значение (камера может округлить его) и среднюю яркость V по каждому ROI из конфига. Цель — выбрать значение, при котором диоды хорошо читаются, без выброса в белое (V ≈ 200-250, без постоянного «залипания» WHITE).

## 8. Наблюдение в реальном времени

### Таблица с перерисовкой (удобно вживую, в SSH-терминале)

```bash
python3 run_linux.py monitor --config config/leds.tsv --exposure 500
```

Таблица перерисовывается на месте (cursor-up), без засорения скроллбека. Ниже таблицы выводятся **последние смены состояний**. Для SSH-терминала (TTY) включены ANSI-цвета по состояниям (`OFF`, `SOLID_ON`, `BLINK_1HZ`, `BLINK_4HZ`, `UNKNOWN`, `CALCULATING`, `NO_DATA`).

### Только лог изменений (append-only, идеален для `nohup`, `tee`, логов)

```bash
python3 run_linux.py log --config config/leds.tsv --exposure 500 --log ledspector_changes.log
```

Пишет в консоль только строки вида:

```
[12:34:56] PWR      OFF          -> SOLID_ON     GREEN
```

Одновременно дублирует изменения в указанный лог-файл.

Параметры:

- `--window 2.0` — окно усреднения частоты мигания (2.0с). Больше окно — точнее частота, медленнее реакция на смену режима; меньше — быстрее, грубее оценка.
- `--interval 0.1` — пауза между кадрами (≈10 FPS).
- `--brightness-only` — анализ только по яркости, без HSV-классификации цвета (полезен при отладке калибровки).
- `--no-events` — отключить блок последних событий в режиме `monitor`.

Одинаковый набор флагов есть у `monitor` и `log` (кроме `--no-events`, который в `log` не нужен — там выводятся только события).

### Снимок кадра с разметкой прямо во время наблюдения

Чтобы посмотреть, что именно камера видит в данный момент, не останавливая наблюдение:

```bash
python3 run_linux.py monitor --config config/leds.tsv --annotated debug.png
```

Далее в любой момент нажми **Ctrl+\\** (или `kill -QUIT <pid>`) — текущий кадр сохранится в `debug.png` с нарисованными прямоугольниками ROI и (по умолчанию) координатной сеткой. Флаг `--annotated-no-grid` сохраняет кадр только с разметкой LED, без сетки.

По умолчанию ничего не пишется: файлы появляются только по этому флагу и только по запросу, поэтому диск не растёт сам по себе.

## 9. Проверка без камеры

Логика (парсер конфига, сетка, анализ цвета и частоты) проверяется на синтетических кадрах без реального устройства:

```bash
python3 test_headless.py
```

Скрипт не требует pytest и ничего не устанавливает: камера подменяется заглушкой, кадры генерируются кодом. Покрыты парсинг и устойчивость конфига, точность координат сетки, обрезка ROI, распознавание цветов, детекция смен состояний, форматирование таблицы и сохранение аннотированного кадра.

## 10. Экспозиция: как работает

Используем два пути выставления экспозиции:

1. **v4l2-ctl** (приоритет) — прямые ioctl, надёжнее всего под Linux. Требует пакет `v4l-utils`. Порядок обязателен: сначала `auto_exposure` в ручной режим, иначе камера тут же перезапишет экспозицию своим значением.
2. **OpenCV (fallback)** — `CAP_PROP_AUTO_EXPOSURE=0.25` (manual) + `CAP_PROP_EXPOSURE=<N>`.

Две детали, из-за которых значения нельзя просто зашить в код:

- **Имя контрола.** У этой камеры он называется `exposure_time_absolute` (0x009a0902). Короткое `exposure_absolute` из спецификации UVC драйвер не принимает — с ним команда молча возвращает пустое значение.
- **Нумерация меню `auto_exposure` различается.** У нас в списке контролов `min=0 max=3 default=3 value=1 (Manual Mode)` — то есть **Manual Mode = 1**, а не 3. Поэтому значение не захардкожено: код разбирает вывод `v4l2-ctl --list-ctrls`, находит строку `auto_exposure` и берёт число из подписи режима. Так сработает и на других камерах, в том числе с обратной нумерацией.

После установки команда `exposure` всегда читает фактическое значение обратно и сообщает, каким путём оно применилось (`method: v4l2-ctl` или `opencv`). Если камера округлила запрос, выводится и запрошенное, и фактическое.

Проверить разбор вручную:

```bash
v4l2-ctl -d /dev/video0 --get-ctrl=exposure_time_absolute
v4l2-ctl -d /dev/video0 --list-ctrls-menus | grep -A3 auto_exposure
```

## 11. Ограничения/примечания

- **PNG, не JPEG.** Кадры для разметки сохраняем в PNG. Снимок по сети — в JPEG, артефакты в нём есть, но на диоде 2-5 px они малы и на разметку не влияют. `snapshot_raw.png` оставлен в PNG как эталон для будущей калибровки цвета.
- **Формат потока MJPG.** Разрешение 1280x720 доступно только в нём, см. раздел 1a. Компромисс — JPEG-сжатие кадра и 20 FPS; для калибровки цвета есть запасной режим `--fourcc yuyv`.
- **Разрешение привязано к конфигу.** Координаты из конфига зависят от разрешения кадра. Монитор сверяет фактическое разрешение с директивой `resolution` и падает при несовпадении — так исключается «тихое» смещение координат.
- **Mean-based HSV.** Классификация использует среднее по всему ROI (как в исходном коде). Поэтому ROI должен плотно охватывать светодиод (3×3 — оптимально). Слишком большой ROI будет усреднять фон и классифицировать как `OFF/BLACK`.
- **Только 1Гц/4Гц.** `FrequencyAnalyser` сейчас распознаёт только `BLINK_1HZ` и `BLINK_4HZ`. Промежуточные/другие частоты попадут в `UNKNOWN` — это поведение исходного модуля, не меняли. С учётом 20 FPS потолок измерения — частота Найквиста 10 Гц.
- **Headless-режим.** В `monitor` при выводе не в TTY (pipe, файл) автоматически переключается на append-only `log`, чтобы не генерировать «картинку» с курсор-управлением.

## 12. Быстрый чек-лист первого запуска

1. `python3 test_headless.py` — логика работает (камера не нужна).
2. `python3 run_linux.py check` — ждём `MJPG 1280x720@20` и `exposure=500`.
3. `python3 run_linux.py grid` — появились `snapshot_raw.png` и `snapshot_grid.png`.
4. По сетке заполняешь 3-5 ключевых LED в `config/leds.tsv`.
5. `python3 run_linux.py exposure --config config/leds.tsv` — подбираешь экспозицию.
6. `python3 run_linux.py monitor --config config/leds.tsv --exposure <значение>` — смотришь состояния вживую, убеждаешься, что координаты верны.
7. При длительном наблюдении — `python3 run_linux.py log ... --log ledspector_changes.log`.

Готово. Фундамент есть, цветовая калибровка — отдельно, как и планировалось.
